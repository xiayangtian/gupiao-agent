# 方案设计台账 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 建立可查询、可查看并可从当前对话直接启动历史实施计划的方案设计台账。

**Architecture:** 以 `docs/superpowers/DESIGN-REGISTRY.md` 作为唯一人工维护的状态源，顶部仅展示未完成项目，完整表保留所有设计的唯一主记录。一个轻量 pytest 守护文档链接、状态枚举与覆盖关系；项目级 `AGENTS.md` 规定新设计、开始执行和完成合并时的台账更新，以及“执行方案：<方案名称>”的解析和执行协议。

**Tech Stack:** Markdown、Python 3.12、pytest、Git、现有 Pi/Superpowers 工作流。

**Spec:** `docs/superpowers/specs/2026-09-14-方案设计台账-design.md`

## Global Constraints

- 台账只服务于方案查询、历史方案查看和方案执行状态；不得包含 `less` 或其他全局 TUI 命令规则。
- `docs/superpowers/DESIGN-REGISTRY.md` 是唯一状态源；“未完成项目”区域只能链接到“全部设计”的主记录，不能复制状态或证据字段。
- 全部设计中的每份 `docs/superpowers/specs/*.md` 必须恰有一条主记录。
- 状态只能为 `待实现`、`实施中`、`已实现`、`待核实`；无可靠合并与验证证据时不得标记 `已实现`。
- 只有 `待实现` 且实施计划已存在的条目可以标记 `可直接执行`；仅有设计时必须标记 `先补计划`。
- 用户说“执行方案：<方案名称>”时，先读取条目的设计和实施计划，在隔离工作区按历史计划执行；开始前更新为 `实施中`，验证合并后才更新为 `已实现`。
- 不新增第三方依赖，不创建 Web 页面、CLI 或自动 Git 历史推断。

- [ ] **Step 1: 写失败的台账契约测试**

创建 `tests/unit/test_design_registry.py`：

```python
from pathlib import Path
import re

ROOT = Path(__file__).resolve().parents[2]
REGISTRY = ROOT / "docs/superpowers/DESIGN-REGISTRY.md"
SPECS = ROOT / "docs/superpowers/specs"


def _all_design_rows():
    text = REGISTRY.read_text(encoding="utf-8")
    section = text.split("## 全部设计", 1)[1]
    return [line for line in section.splitlines() if line.startswith("|") and "---" not in line]


def _spec_targets(row):
    return re.findall(r"\]\((specs/[^)]+\.md)\)", row)


def test_every_design_spec_has_one_primary_registry_row():
    rows = _all_design_rows()
    recorded = [target for row in rows for target in _spec_targets(row)]
    expected = sorted(path.relative_to(REGISTRY.parent).as_posix() for path in SPECS.glob("*.md"))
    assert sorted(recorded) == expected
    assert len(recorded) == len(set(recorded))


def test_registry_lists_unfinished_items_and_uses_only_allowed_values():
    text = REGISTRY.read_text(encoding="utf-8")
    assert text.index("## 未完成项目") < text.index("## 全部设计")
    assert "待实现" in text or "实施中" in text or "待核实" in text
    for row in _all_design_rows():
        assert sum(status in row for status in ("待实现", "实施中", "已实现", "待核实")) == 1
        assert sum(mode in row for mode in ("可直接执行", "先补计划", "—")) == 1


def test_project_workflow_defines_registry_updates_and_direct_execution():
    policy = (ROOT / "AGENTS.md").read_text(encoding="utf-8")
    for requirement in (
        "DESIGN-REGISTRY.md",
        "执行方案：<方案名称>",
        "实施中",
        "已实现",
        "验证",
    ):
        assert requirement in policy
```

### Task 2: 建立台账并回填历史设计

**Files:**
- Create: `docs/superpowers/DESIGN-REGISTRY.md`

**Interfaces:**
- Consumes: `docs/superpowers/specs/*.md`、同主题 `docs/superpowers/plans/*.md`、`.superpowers/sdd/` 进度记录、`main` 合并提交。
- Produces: 未完成索引和全量主记录；每个设计文档一个完整表格行。

- [ ] **Step 1: 写入台账固定结构**

创建文件并按以下结构写入，标题下明确“状态依据为人工核对的方案、进度和已合入验证证据；不以文件名推测完成状态”：

```markdown
# 方案设计台账

本台账是已完成方案设计的唯一执行状态源。优先查看“未完成项目”；每条均可跳转到历史设计和实施计划。

## 未完成项目

| 方案 | 状态 | 可执行性 | 方案入口 |
|---|---|---|---|

<!-- 仅列出全部设计表中状态为待实现、实施中或待核实的条目；链接使用对应主记录锚点。 -->

## 全部设计

| 方案 | 设计文档 | 实施计划 | 实现状态 | 可执行性 | 实现证据 | 更新日期 |
|---|---|---|---|---|---|---|
```

- [ ] **Step 2: 回填每份已跟踪设计文档**

对 `docs/superpowers/specs/` 中每一份 `.md` 创建一行“全部设计”主记录。设计链接必须使用 `specs/<文件名>`；同主题且实际存在的实施计划使用 `plans/<文件名>`；不存在时填写 `未创建`。

状态核对顺序必须是：

1. 读取同主题实施计划、任务报告和进度文件；
2. 用 `git log --merges --oneline` 及合并提交变更确认是否确实合入 `main`；
3. 在计划或测试证据中确认实际验证命令/结果；
4. 仅当第 2、3 步均成立时写 `已实现` 并记录短 SHA 和验证摘要；
5. 有现存实施分支或进度文件而未合并的写 `实施中`；
6. 有设计和计划但无进行中或已实现证据的写 `待实现`；
7. 历史资料不足的写 `待核实`，证据栏写明“缺少可验证的合并/验证记录”。

可执行性填写规则：`待实现` 且实施计划存在写 `可直接执行`；仅有设计写 `先补计划`；`实施中`、`已实现` 和 `待核实` 写 `—`。

- [ ] **Step 3: 生成未完成项目索引**

从“全部设计”中逐条复制**仅**方案名称、状态、可执行性和主记录锚点到“未完成项目”。不要复制设计、计划、证据或更新日期。按 `待实现`、`实施中`、`待核实` 排序；同状态内按更新日期降序。

### Task 3: 固化维护与“按历史方案执行”协议

**Files:**
- Create: `AGENTS.md`

**Interfaces:**
- Consumes: `docs/superpowers/DESIGN-REGISTRY.md` 的方案名称、状态、可执行性、设计链接和实施计划链接。
- Produces: 后续代理必须遵守的台账维护时点及直接执行行为。

- [ ] **Step 1: 新增项目级协议**

创建根目录 `AGENTS.md`，写入“方案设计台账”章节，必须包含以下可执行规则：

```markdown
## 方案设计台账

- `docs/superpowers/DESIGN-REGISTRY.md` 是已完成设计方案的唯一执行状态源；新设计获确认后登记为 `待实现`。
- 创建实施分支或开始按计划修改前，先将对应条目更新为 `实施中`，并记录分支名或进度文件。
- 用户说“执行方案：<方案名称>”时：从台账精确匹配唯一名称；读取设计文档和实施计划；仅当状态为 `待实现` 且可执行性为 `可直接执行` 时，在隔离工作区按原计划执行。不得重新设计、跳过计划或把相似方案当作目标。
- 条目为 `先补计划` 时，先补齐实施计划并取得确认，不得直接编码。
- 只有适用验证通过且工作合入 `main` 后，才将条目更新为 `已实现`，并记录合并短 SHA、验证命令和结果；失败、暂停或范围变化保持为未完成并说明原因。
```
