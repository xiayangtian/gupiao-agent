# 智能问答财报补充下载 — 设计方案

**Date:** 2026-09-14  
**Status:** scoped  
**Scope:** 当智能问答缺少回答所必需的本地财报 PDF 证据时，提出最多 5 份受控候选报告；仅在用户勾选并一次确认后下载、摄取并继续回答。**不包含**无授权下载、自动财报 AI 分析、行业范围的批量补库、网页或 MCP 数据下载，或跨提问复用下载额度。

---

## 1. 现有业务模型

### 已存在的概念与能力

| 概念 | 当前事实 | 终态 / 义务 |
|---|---|---|
| 问答 Scope | 当前问答在服务端解析 `company_only`、`company_industry`、`whole_corpus`；财报检索可按 Scope 硬过滤 | 不得以检索优先级绕过 Scope |
| RAG 检索 | `RagQA.answer_stream()` 按本地索引片段回答，并已有 MCP/网页工具编排 | 本地 PDF 是财报数字和披露的确定性证据 |
| 报告元数据 | `CNINFODatasource` 和现有报告索引可提供 `ReportMeta`；本地 PDF 文件名及 `report_id` 有统一身份规则 | 下载候选必须来自受控元数据，不能由模型提供 URL |
| PDF 下载 | `ReportDownloader.download_one()` 有有效 PDF 校验、重试和原子落盘 | 只下载明确的 `ReportMeta`，已有有效 PDF 幂等跳过 |
| RAG 摄取 | `IngestionService.auto_ingest_pdf()`/`ingest_one()` 可把单份 PDF 入库 | 下载后必须先成功摄取，才可作为重新回答的证据 |
| 会话运行 | `ChatStore` 保存 `AnswerRun`、Scope、来源、状态与最终回答 | 用户授权、拒绝、失败和补充来源不能只存在于临时前端状态 |

### 当前未建模的概念

- **财报补充请求（Supplement Request）**：一条问题与一批受控候选报告、一次用户授权和一次额度之间的可审计关系；
- **补充候选（Supplement Candidate）**：由服务端解析出的报告身份、来源、排序理由和本地可用性，不是模型自由文本；
- **用户授权事件（Consent）**：用户选择、拒绝或超时，必须能阻止重放和越权下载；
- **恢复回答（Resumed Answer）**：下载和摄取后，对同一问题再运行一次回答，并显式区分补充前后证据。

## 2. 用户任务与信息架构

用户提出财报问题时，希望得到有证据的回答；当现有本地报告不足时，用户愿意按需补充，但需要在下载发生前知道会下载什么，并控制数据量。

问答流中新增的业务节点是一个**需要用户决定的授权项**，不是错误提示或普通工具日志。首屏授权卡必须回答：

1. 为什么当前证据不足；
2. 拟下载哪些公司、报告期和报告类型；
3. 每项来自什么受控数据源；
4. 当前提问还能选择多少份（最大 5）；
5. 确认后系统会下载、摄取并重新回答；拒绝后将用现有证据回答。

授权卡不显示内部工具名、模型提示词、下载 URL 或向量库实现细节。

## 3. 业务边界与决策

### 3.1 触发条件

仅当同时满足以下条件才允许提出补充请求：

1. 问题属于已解析的**单一目标公司** Scope；
2. 模型在现有检索证据下明确判定“缺少必要的财报披露”，并以受控 `request_missing_reports` 工具调用表达所需报告期/类型；
3. 后端能够从受控报告数据源将该需求解析为未本地入库的有效 `ReportMeta`；
4. 候选不超过 5 份且至少有一份可下载。

首期不为 `whole_corpus`、无公司上下文或行业比较自动下载财报；这些问题必须明确说明缺少可核验本地报告。这避免把“补充本公司必要披露”扩展成不受控的同业批量采集。

### 3.2 候选排序与上限

候选由服务端按下列顺序筛选和排序：

1. 与问题明确提及的报告期、报告类型精确匹配；
2. 与当前 Scope 的目标公司匹配；
3. 最新完整年度/半年年度报告优先于季度报告；
4. 同等条件按报告披露日期倒序。

过滤掉本地已有有效 PDF、已入 RAG 的报告、无下载 URL、重复 `report_id` 和不在 Scope 中的报告。服务端最多保留前 5 项；模型提出更多或无效需求时不扩大上限。

“最多 5 份”是**单次提问生命周期**的预算：从初始提问、授权、下载、摄取到恢复回答结束为止。确认的候选数计入预算；同一补充请求不可再次消费。下一条用户问题重新获得 5 份预算。

### 3.3 授权和防重放

服务端创建不可预测的 `supplement_id`，将其绑定到 `session_id`、规范化问题摘要、目标 Scope、候选 `report_id`、额度、创建时间和状态。用户只能在创建它的会话中选择该候选集合中的 ID；选择数必须在 `1..5` 且不超过剩余额度。

补充请求状态：

```text
proposed → approved → downloading → ingesting → resuming → completed
         ↘ declined
         ↘ expired
         ↘ failed
```

- `proposed` 仅展示候选，不产生下载；
- `approved` 是唯一允许下载的状态，使用后立即消费；
- `declined`、`expired`、`failed` 均不可再次批准；
- 重复提交、跨会话提交、候选篡改、超过 5 份和已消费请求均返回明确错误，绝不下载。

授权状态和候选摘要必须随会话/AnswerRun 持久化；不保存下载 URL 或用户不需要的内部错误堆栈。

## 4. 数据与接口契约

### 4.1 模型工具契约

在已有工具编排中添加仅用于“请求补充”的工具定义：

```json
{
  "name": "request_missing_reports",
  "description": "仅当当前本地财报证据不足且必须补充 PDF 披露才能回答时调用；不能下载文件。",
  "parameters": {
    "type": "object",
    "required": ["reason", "needs"],
    "properties": {
      "reason": {"type": "string", "maxLength": 240},
      "needs": {
        "type": "array",
        "maxItems": 5,
        "items": {
          "type": "object",
          "required": ["period", "report_type"],
          "properties": {
            "period": {"type": "string"},
            "report_type": {"enum": ["annual", "semi_annual", "quarterly"]}
          }
        }
      }
    }
  }
}
```

模型工具调用不直接执行下载。`RagQA` 把该调用上交为 `supplement_needed` SSE 事件并停止本轮最终回答；服务端负责候选解析、持久化和授权。

### 4.2 SSE 事件

初始 `/api/chat/stream` 在提出候选时发送：

```json
{
  "type": "supplement_needed",
  "supplement_id": "opaque-id",
  "reason": "当前本地仅有 2024 年报，无法核验 2025 年上半年变化。",
  "limit": 5,
  "candidates": [
    {
      "id": "candidate-opaque-id",
      "company": "农业银行",
      "code": "601288",
      "period": "2025-06-30",
      "report_type": "semi_annual",
      "label": "2025 半年报",
      "source": "巨潮资讯"
    }
  ]
}
```

不发送下载 URL、文件系统路径或模型原始工具参数。此事件后初始流结束并保存状态 `proposed`。

### 4.3 授权恢复端点

新增 `POST /api/chat/supplements/{supplement_id}/resolve`，请求体：

```json
{
  "session_id": "abc123",
  "action": "approve",
  "candidate_ids": ["candidate-opaque-id"]
}
```

- `approve`：验证后以 SSE 依次发送 `supplement_download_started`、`supplement_downloaded`、`supplement_ingested`、`supplement_failed` 和既有 `run_started`/`delta`/`done`；
- `decline`：不接受 `candidate_ids`，保存 `declined`，返回基于既有证据的终结回答流；
- 任何下载或摄取失败只影响该候选；成功摄取的报告仍用于恢复回答；若全失败，终结回答必须说明不能补充的原因。

恢复回答使用原问题、原模型上下文和成功入库的 `report_id`，且答案运行记录新增 `supplement` 摘要：授权结果、成功/跳过/失败报告、来源和恢复时间。

## 5. 前端交互

- 收到 `supplement_needed` 后停止“正在回答”状态，显示授权卡；
- 候选以复选框列出，默认不选；确认按钮显示“下载并继续回答（已选 N/5）”，没有选择时不可用；
- “暂不下载，基于现有信息回答”发送 `decline`；
- 确认后按钮禁用，实时展示“正在下载 1/3”“正在摄取”等业务化状态；
- 成功恢复后，在答案来源摘要中显示“本次经授权补充 X 份财报”；
- 失败项显示公司、报告期和可理解原因，但不暴露 URL/异常堆栈；
- 需要键盘可操作、可见焦点、语义化复选框/按钮和 `aria-live` 进度通知；移动端无横向溢出。

## 6. 错误与降级

| 场景 | 系统行为 |
|---|---|
| RAG 足以回答 | 不创建补充请求，不显示授权卡 |
| 模型未提出受控补充需求 | 按既有问答回答 |
| 无公司 Scope / 行业比较 | 不提供自动下载，说明范围限制 |
| 无候选或候选均已本地可用 | 不显示授权卡，按现有证据回答 |
| 用户拒绝 | 不下载，保存拒绝并完成现有证据回答 |
| 下载部分失败 | 摄取成功项并恢复回答；列出失败项 |
| 全部下载或摄取失败 | 不重试、不改写原问题；完成带缺口说明的回答 |
| 授权过期/重放/篡改 | 拒绝请求，不下载；要求用户重新提问 |

## 7. 验收标准

- 未经用户批准，任何问答路径不得调用 `ReportDownloader.download_one()`；
- 单次提问生命周期内服务端批准候选数永远不超过 5；
- 候选均来自受控元数据、当前单公司 Scope 且不含本地已可用报告；
- 取消、过期、跨会话和重复授权均无法触发下载；
- 已批准报告下载后先摄取，成功摄取的 `report_id` 才进入恢复回答；
- 下载失败/拒绝仍会产生诚实的终结回答，不无限等待或自动下载；
- 授权、选择、结果和恢复回答摘要可在会话历史中重开查看；
- 单元测试覆盖候选上限、排序、授权验证、消费、拒绝、部分失败和恢复上下文；浏览器测试覆盖授权卡、选择上限、拒绝、确认恢复、键盘操作和移动端无横向溢出。

| 模型能给出要下载的报告 URL | 模型可提出所需披露类型，但报告候选、来源和下载身份必须由服务端解析和验证 | implementation | refined | P-05 |
| 五份限制只是 UI 限制 | 数据量限制属于一次提问的业务预算，必须由服务端绑定问题、授权和消费状态 | implementation | refined | P-01 |
| 缺少财报时只能回答“没有信息” | 用户可以选择补充证据；授权、拒绝和下载失败是问答运行的不同终态 | represented | refined | P-04 |
