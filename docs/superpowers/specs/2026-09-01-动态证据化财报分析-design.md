## 1. 业务当前实际建模的内容

### 1.1 已存在的业务概念

- **财务报告**：以公司代码和报告期唯一识别，PDF 是本地保存和预览的法定披露文件。
- **分析任务**：用户选择若干分析维度后创建后台任务，任务可持久化、取消、查询进度，并在完成后生成 Markdown 和 JSON 报告。
- **分析维度**：当前由预设提示词定义；每个维度产生一段模型回复，前端将其显示为固定 Tab。
- **RAG 片段**：PDF 按页面和章节抽取、分块并建立向量索引；维度分析可检索相关片段，失败时回退到截断正文。
- **结构化指标**：分析结束后由模型额外抽取少量年度指标，保存为图表数据和财务事实。
- **分析历史**：已生成报告可在历史页查看，也可以基于用户重新选择的维度发起重新分析。

### 1.2 状态的业务含义

| 状态 | 业务含义 | 用户需要做什么 |
| --- | --- | --- |
| 排队 / 处理中 | 后台尚未产生可消费结果 | 等待，或离开页面继续其他操作 |
| 快速结论可读 | 已有最小可用、经过校验的结果 | 可以开始阅读；无需等待全部深度分析 |
| 深度分析中 | 系统正在补充 OCR、图表和主题证据 | 无需停留；可查看实时进度 |
| 完成 | 所有可展示主题已终止处理 | 阅读结果或继续对话 |
| 部分完成 | 部分来源或主题失败，但已有有效结果 | 阅读成功部分，并决定是否重试失败部分 |
| 失败 | 未形成任何可消费结果 | 查看原因并重试 |

现有系统只建模“排队 / 处理中 / 完成 / 失败 / 取消”及一个总体进度值。`快速结论可读`、`深度分析中`和`部分完成`属于本设计新增的业务状态。

### 1.3 动作产生的业务事件

- **开始分析**：为一份报告创建可恢复的分析任务；用户选择的是关注方向，而不是必须生成的 Tab。
- **重新分析**：基于同一报告和新关注方向创建新分析版本，复用未变化的数据与解析缓存。
- **停止分析**：停止尚未完成的后台工作，已提交的有效结果继续保留。
- **查看结果**：打开与公司、报告期和分析版本绑定的结果，不改变任务状态。
- **继续对话**：围绕指定报告和分析版本开启独立对话，不在报告阅读页面内延续旧会话。

### 1.4 当前业务没有建模的概念

- 报表主体（合并、母公司、未知）及其不可混用约束。
- 带来源、页码、区域、单位和校验状态的统一证据。
- PDF 页面质量和“是否需要 OCR”的判断。
- 图表或复杂表格的结构化解析结果。
- 动态候选主题、主题质量分、淘汰原因和排序依据。
- 快速结论与深度主题相互独立的结果生命周期。
- 可断线续传的分析事件流。

这些都是领域扩展，不应被当成提示词调整或前端样式优化。

## 2. 用户视图模型

### 2.1 使用情境与任务

**已报告的用户需求：** 当用户打开一份年报时，希望先快速知道最值得关注的少量结论，同时确信数字没有混用主体、没有凭空补全；更细致的分析可以在后台继续，并在完成后自动出现。

用户不是来检查模型执行了多少个预设维度，而是要回答：

1. 这份报告最重要的变化是什么？
2. 哪些结论已有可靠证据，哪些仍待核验？
3. 这些数字来自哪个主体、报告期和页面？
4. 还有哪些深入主题值得继续阅读？

### 2.2 用户查找对象

- **首屏查找对象：关键结论。** 每条直接附关键数据、影响和证据状态。
- **深入查找对象：动态主题。** 每个主题直接附 3～5 条关键发现及可展开证据。
- **次要维度：** 数据源、页码、OCR 区域、任务步骤、内部评分和分析版本。它们用于解释来源、筛选或审计，不主导默认阅读结构。

### 2.3 首次扫描应直接回答的问题

- 快速结论是否已经可读？
- 后台还在处理什么，预计是否值得继续等待？
- 当前最重要的三条结论是什么？
- 结论属于合并口径还是母公司口径，是否经过交叉验证？

### 2.4 证据与置信度

- 用户明确报告了固定模板经常产生无数据内容、Tab 过多、强调过量和等待时间长的问题。
- 用户确认选择维度应改为关注方向，最终 Tab 可动态生成、过滤和排序。
- 用户确认快速结论独立 Tab、后台运行提示和详细结果自动推送的界面方向。
- 30 秒和 90 秒目标是设计目标，尚未用生产模型、真实网络和黄金财报集测量，属于待验证假设。

## 3. 结构性诊断

当前页面把实现模型中的“固定提示词维度”直接映射为用户看到的 Tab。结果是系统为了完成执行清单而生成内容，而不是为了帮助用户形成可靠判断：没有数据的维度仍被尝试，模型被迫面对截断或错位文本，合并与母公司口径可能混入同一上下文，用户还要从大量加粗和标红文字中重新寻找重点。

问题不是模板写得不够好，而是缺少位于模型生成之前的**证据层和动态主题决策层**。固定 Tab、长内容和错误强调只是这个结构错误在界面上的表现。

另一个结构错误是任务只有“完成后交付”的单阶段模型。快速可用结果和深度分析被绑在一起，少量关注方向也必须等待整条流水线，因此用户无法判断等待是否值得。

## 4. 设计原则

### 4.1 先形成证据，再生成结论

任何确定性数字结论必须绑定公司、报告期、报表主体、单位和来源位置。

**拒绝方案：** 继续把整段 PDF 文本交给模型，并用“不要编造”提示词代替数据约束。

### 4.2 PDF、结构化数据和 OCR 各司其职

- PDF 是最终法定披露依据。
- 官方或配置的数据源是数值分析的主要入口。
- OCR 只补充原生文字层和结构化数据没有覆盖的表格、图表及扫描页面。

**拒绝方案：** 完全依赖第三方结构化接口，或对整份 PDF 无差别执行 OCR/VLM。

### 4.3 用户选择的是关注方向，不是输出合同

选择方向影响处理优先级和主题相关性，但不能强迫系统返回没有证据的 Tab；高价值额外发现可以动态加入。

**拒绝方案：** 勾选几个维度就固定生成几个 Tab。

### 4.4 可读结果不等待完整流水线

快速结论与深度分析解耦；满足最低证据要求后立即交付快速结果，后台继续增强。

**拒绝方案：** 只显示一个总体百分比，所有内容完成后一次性返回。

### 4.5 密度由判断价值决定

默认只显示少量结论和关键发现；证据细节按需展开。特殊样式的数量由重要性决定，而不是由模型输出习惯决定。

**拒绝方案：** 通过缩小字号或继续压缩长篇 Markdown 来制造“精简感”。

## 5. 总体架构与数据流

### 5.1 推荐路线：混合证据流水线

```text
报告身份
  ├─ 结构化数据适配器 ─┐
  └─ PDF 原生解析 ─────┼─> 证据归一化与冲突检测 ─> 快速结论
          └─ 页面质量检测 ─> 按需 OCR / 表格 / 图表解析 ─┘
                                      ↓
                            动态候选主题发现与评分
                                      ↓
                       高分详细主题逐项保存并实时推送
```

选择混合路线的原因：结构化数据在三大报表数字和主体口径上更可靠；PDF 原文保留法定证据及经营叙述；按需 OCR 补充图表和视觉表格。三者互相校验，而不是互相替代。

### 5.2 组件边界

#### StructuredDataGateway

统一数据源协议，负责按公司和报告期获取三大报表、财务指标及主体口径。默认接入无需用户配置的公开来源；配置 Tushare Token 后优先使用 Tushare；后续可接交易所 XBRL 或授权数据源。

每个提供方必须返回来源、抓取时间、报告期、主体、调整状态和原始字段，不得只返回归一化数字。

#### DocumentExtractor

提取 PDF 原生文字、页面布局、嵌入图片及初步表格结构，并为每页生成质量指标，例如文字字符密度、异常字符比例、表格对齐度和视觉区域占比。

#### OcrEnricher

仅处理以下页面：原生文字过少、关键表格错位、候选主题需要但证据缺失、或检测到关键图表。推荐使用 PaddleOCR PP-StructureV3 一类支持版面、表格和图表解析的本地能力，并将模型版本写入缓存键。

#### EvidenceResolver

统一单位、币种、报告期、报表主体和调整状态；合并相同事实；比较跨来源数值；输出通过验证、单一来源、冲突或主体未知状态。

#### InsightPlanner

读取关注方向和证据目录，发现显著变化、异常、趋势及具有解释价值的经营事实，并聚合为候选主题。它只规划主题，不生成面向用户的长文。

#### InsightAnalyzer

针对单个主题生成统一结构：一句核心结论、3～5 条关键发现、影响判断、证据引用和置信度。固定的是输出契约与质量约束，不是主题内容模板。

#### AnalysisCoordinator

编排快速与深度任务、管理有限并行、保存任务快照和事件、处理取消与恢复，并确保快速任务不被 OCR 或大量深度模型请求饿死。

### 5.3 统一证据记录

每条证据至少包含：

| 字段 | 含义 |
| --- | --- |
| `report_id` | 公司、报告期和报告类型组成的稳定身份 |
| `entity_scope` | `consolidated`、`parent` 或 `unknown` |
| `fact_name` | 规范化指标或事实名称 |
| `value` / `unit` / `currency` | 数值及口径 |
| `period` | 年度、季度或时点 |
| `source_type` | XBRL、结构化接口、PDF文字、OCR表格、图表或正文 |
| `source_locator` | 接口、页码、表格标题、区域坐标或原始记录标识 |
| `extraction_confidence` | 提取本身的可信度 |
| `verification_state` | 已交叉验证、单一来源、冲突、主体未知 |
| `content_hash` / `parser_version` | 缓存与可复现性 |

### 5.4 来源权威与冲突处理

- 结构化数据与 PDF 一致：提高可信度。
- 结构化数据缺失、PDF 明确披露：保留 PDF 事实。
- PDF 原生解析失败但 OCR 稳定识别：保留 OCR 事实并降低提取置信度。
- 不同来源冲突：保留双方证据和差异，不自动选择一个值生成确定性结论。
- 合并与母公司同时存在：分别存储，默认分析合并口径；需要母公司判断时明确标记。
- 主体未知：禁止参与跨期比率和合计计算。

参考现实来源：上交所公开页面说明经营业绩数据来自上市公司 XBRL 报告，但仍以 PDF 为准；AKShare 可获取公开三大报表；Tushare 提供并区分合并、母公司及调整报表类型。提供方必须可替换，不能把一个非官方页面接口写死为业务真相。

## 6. 动态主题、评分与结果契约

### 6.1 主题发现

1. 快速扫描结构化事实和高质量正文，识别显著变化及异常。
2. 按用户关注方向优先组织候选主题。
3. 背景阶段从 OCR、图表和附注中补充额外候选。
4. 合并语义相近主题，避免同一事实重复出现在多个 Tab。
5. 单主题生成后先完成证据校验，再进入评分。

### 6.2 评分模型

| 维度 | 分值 |
| --- | ---: |
| 证据充足度 | 30 |
| 来源可靠性与交叉验证 | 25 |
| 对经营或投资判断的重要性 | 20 |
| 结论清晰度与可解释性 | 15 |
| 与用户关注方向的相关性 | 10 |

展示门槛：

- 75 分以上：正式详细 Tab。
- 60～74 分：不得进入三条核心结论；如确有时效价值，只能放入快速 Tab 内独立的“待验证观察”区域，不得写成确定性结论。
- 60 分以下：不向用户展示，保留淘汰原因供调试和质量评估。
- 任何主体混用、重大数值冲突或无证据定位主题直接失去确定性结论资格。

阈值应配置化，并通过黄金财报集校准；不应分散为提示词中的隐含规则。

### 6.3 快速结论

- 始终为独立且第一个 Tab。
- 最多三条已经验证、最值得先看的结论。
- 每条包括一句判断、关键数据、影响解释和证据状态。
- 可在核心结论之后附少量“待验证观察”，但必须与核心结论视觉隔离，且不占用核心结论名额。
- 不等待 OCR 完整运行；暂缺的深度证据只影响对应主题。
- 原则上不被后台静默重写。深度证据推翻初步判断时，必须生成显式修正事件和修正原因。

### 6.4 详细主题

- Tab 名称来自实际主题，不来自固定维度列表。
- 每个 Tab 包含一句核心判断、3～5 条发现，必要时附一个精简表格或图表。
- 证据区默认收起，展开后可查看来源、主体、页码、表格区域和计算过程。
- 默认最多六个详细 Tab；没有高质量主题时可以只有快速结论。
- 内部评分仅用于过滤和排序，界面不展示“92分”一类容易被误解为投资评级的数字。

## 7. 渐进任务、事件流与前端状态

### 7.1 任务生命周期

```text
queued
  → fast_processing
  → fast_ready
  → deep_processing
  → completed | partial | failed | cancelled
```

`fast_ready` 是可消费状态，不是完成百分比。用户可以开始阅读，同时后端继续工作。

### 7.2 调度策略

- 结构化数据和 PDF 原生解析并行。
- 最低可用证据满足后立即启动快速结论。
- 用户选择的 1～2 个方向先进入深度队列，不提前执行全部潜在主题。
- OCR 和额外主题发现使用较低优先级，避免占满模型与 CPU 资源。
- 每个主题独立提交、校验和保存；一个主题失败不回滚已完成结果。
- 所有解析缓存按 PDF 内容哈希、提供方版本和解析器版本命中。

### 7.3 持久化事件

建议事件包括：

- `job.stage_changed`
- `quick.ready`
- `extraction.page_started`
- `extraction.page_completed`
- `theme.started`
- `theme.filtered`
- `section.ready`
- `section.updated`
- `quick.corrected`
- `job.completed`
- `job.partial`
- `job.failed`

事件包含单调递增编号。SSE 客户端断线后携带最后事件编号，服务端补发遗漏事件；SSE 不可用时回退任务快照轮询。

### 7.4 前端信息架构

#### 报告标题区

显示公司、报告期和版本，不放内部执行细节。

#### 后台运行条

显示当前阶段、完成数量和正在处理的对象，并明确提示“可以切换页面或关闭窗口，任务不会中断”。完成后转为简洁成功状态。

#### Tab 区

- `快速结论` 固定第一。
- 已完成详细主题按质量和重要性排序。
- 正在处理的主题可显示为不可点击的状态项，而不是空内容 Tab。
- 新结果通过事件自动加入；当前选中 Tab 不跳走。
- 用户开始阅读后不突然重排，只提示新发现。

#### 内容区

- 一条发现通常突出 1～2 处关键数字，必要时可稍多。
- 强调内容总体不超过正文约 20%。
- 红色仅用于已验证风险、恶化或异常。
- 正向重点采用克制的中性强调，不大面积使用绿色。
- 不显示“数据未披露”占位行、空表格和空章节。

## 8. 降级、错误和修正

| 故障 | 行为 |
| --- | --- |
| 默认结构化数据源不可用 | 尝试下一提供方；全部失败时继续 PDF 路径并标记单一来源 |
| PDF 原生文字不足 | 仅对受影响页面执行 OCR |
| 表格或图表解析失败 | 不阻塞其他主题；相关主题降分或过滤 |
| 不同来源数值冲突 | 保存冲突证据，不输出未经说明的唯一值 |
| 主体无法判断 | 不执行跨期或比率计算 |
| 单主题模型调用失败 | 其他主题继续，任务最终可为部分完成 |
| SSE 断线 | 从最后事件编号恢复；失败后回退轮询 |
| 快速结论被深度证据推翻 | 发布显式修正事件，保留修正前后和原因 |
| 旧版分析报告 | 继续可读并标记旧版；重新分析生成新证据化结构 |

## 9. 性能目标

### 9.1 用户可感知目标

- 缓存命中且选择 1～2 个关注方向：约 30 秒内出现快速结论。
- 详细主题逐项推送，尽量在 90 秒内形成主要结果。
- 首次 OCR 可以更久，但不得阻塞已有结构化数据可支撑的快速结果。

### 9.2 性能手段

- 数据源请求与 PDF 原生解析并行。
- PDF、页面质量、OCR、表格、图表和证据目录分别缓存。
- 重新分析仅重跑受关注方向、评分或提示版本影响的步骤。
- 快速任务拥有独立并发配额；深度模型请求有限并行；OCR 队列低优先级。
- 前端按事件增量渲染，不反复下载整份结果。

上述时间是产品目标，不是已经验证的服务等级。实施时需记录 P50、P95 以及缓存冷/热差异。

## 10. 范围：业务目前支持什么

| Bucket | Capability | Meaning |
| --- | --- | --- |
| ✅ 已建模并已暴露 | PDF 下载与预览、报告身份、历史报告、可选关注方向、持久化任务、取消、共享状态 | 可以复用并调整呈现 |
| ✅ 已建模并已暴露 | PDF 分页文本和章节 RAG、报告问答引用、对话 SSE | 可复用底层能力，但不能直接等同于分析证据 |
| ⚠️ 已建模但未用于分析页 | SQLite 任务恢复、聊天事件流、RAG 引用和页码 | 可扩展到分析任务，工程成本仍需验证 |
| ❌ 新领域能力 | 报表主体、统一证据、数据源权威、冲突状态 | 数据模型与迁移成本高，是准确性的前提 |
| ❌ 新领域能力 | 页面质量、按需 OCR、表格和图表结构 | 模型下载、CPU/内存、缓存与跨平台兼容成本 |
| ❌ 新领域能力 | 动态主题、评分、淘汰原因、快速与深度结果 | 分析编排、输出结构和历史格式均需扩展 |
| ❌ 新领域能力 | 分析事件日志与断线续传 | 新持久化结构、SSE API 和前端状态归并 |

**推荐的完整价值切片：** 证据基础层、快速结论、动态主题评分、按需 OCR 和实时推送共同构成一次完整用户任务。可以分阶段实施，但不能用没有主体与证据约束的动态生成冒充完成版本。

**本轮不建设：** 投资评级、买卖建议、自动交易、全量行业横向数据库、付费数据采购和云端 OCR 服务。它们分别涉及合规、授权、持续数据运营和新增基础设施，不是本需求的必要条件。

## 11. 红线

- **系统目前没有“报表主体”概念；在建模完成前不得声称能可靠区分合并与母公司结论。**
- **系统目前没有统一证据概念；无来源定位的模型文本不能升级为确定性事实。**
- **内部质量分不是投资评级，不得以精确分数向用户呈现。**
- **OCR 识别结果不是法定原文；低置信度 OCR 不得覆盖 PDF 或结构化事实。**
- **快速结论不是草稿占位；只有达到最低证据要求才能进入可读状态。**
- **后台任务步骤是审计信息，不应成为报告默认信息架构。**

## 12. 验证与测试策略

### 12.1 黄金财报集

至少覆盖：普通工商企业、银行或保险、扫描页面、复杂跨页表格、图表较多、合并与母公司并存、结构化数据缺失、来源冲突和旧版报告。

### 12.2 自动化验证

- 数据源适配器契约与失败切换。
- 单位、币种、报告期、主体和调整状态归一化。
- 同一事实去重、跨来源一致性和冲突检测。
- 页面质量判断与 OCR 触发边界。
- 候选主题合并、评分、阈值过滤及稳定排序。
- 确定性结论必须带证据引用的结构约束。
- 快速状态、部分完成、取消、重启恢复和事件补发。
- SSE 断线重连、跨页面同步、当前 Tab 保持和无需刷新自动新增。
- 旧版报告兼容读取。

### 12.3 质量指标

- 数字抽取正确率。
- 报表主体识别与主体混用率。
- 无依据确定性结论率，目标为零。
- 来源冲突发现率和错误自动裁决率。
- 低证据主题过滤准确度。
- 用户选择 1～2 个方向时的快速结果 P50/P95。
- 冷启动与缓存命中的 OCR、主题分析耗时。
- 每个 Tab 的发现数量、强调比例和空内容率。

### 12.4 验收标准

- 所有确定性数字可追溯到来源、主体、报告期和页码或接口。
- 合并与母公司数据不混用；未知主体不参与自动计算。
- 冲突数据不生成未经说明的唯一值。
- 证据不足主题不生成 Tab。
- 缓存命中、选择 1～2 个方向时约 30 秒内返回快速结论。
- OCR 不阻塞快速结果。
- 详细主题自动推送，刷新和切页不丢任务。
- 详细 Tab 默认不超过 5 条发现，空项和纯未披露内容为零。
- 单来源、OCR 页或单主题失败不影响其他有效结果。

## 13. 分阶段落地顺序

1. **证据基础层**：数据源适配、主体/报告期/单位规范化、PDF证据定位和缓存。
2. **快速分析层**：独立快速结论、关注方向优先和少量选择快速返回。
3. **动态深度层**：候选发现、评分、过滤、动态排序和精简内容结构。
4. **OCR 增强层**：按需 OCR、表格和图表解析。
5. **实时体验层**：分析事件流、断线续传、跨页同步和详细 Tab 自动推送。

每阶段都必须保持现有历史报告可读。阶段拆分是实施顺序，不改变最终完整价值切片。

## 15. 已确认决策与后续开放项

### 已确认

- 使用混合证据流水线。
- PDF 为最终法定依据，结构化数据为数值主入口，OCR 按需补充。
- 用户选择是关注方向，不是固定 Tab 合同。
- 快速结论独立，详细结果渐进推送。
- 动态主题通过证据和价值评分过滤、排序。
- 每个 Tab 默认 3～5 条发现，特殊样式克制使用。
- 内部质量分不作为用户可见投资评级。
- 今日仅完成设计，不进行代码实现。

### 实施阶段需校准但不改变架构的参数

- 不同行业的评分阈值是否需要差异化。
- 页面质量检测的 OCR 触发阈值。
- 快速阶段最低证据集合。
- 本地 OCR 的 CPU、内存和模型尺寸配置。
- 默认公开数据源的稳定性与限流策略。
- 30 秒 / 90 秒目标在不同模型与硬件上的实际 P50/P95。

这些参数应通过黄金财报集和性能基准确定，不需要重新打开总体架构决策。
