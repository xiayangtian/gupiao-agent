# P0 可靠性修复设计

## 1. 目标与范围

本次只处理三项会直接影响报告正确性或运行可靠性的 P0 问题：

1. 一季报和三季报身份冲突；
2. Web 分析任务状态只保存在内存；
3. LLM 抽取的财务指标缺少统一的结构化事实模型和程序校验。

保持现有 CLI、Web API、Markdown 报告和 JSON 中的 `metrics` 字段兼容。不在本次引入完整 Planner、多 Agent 调度、OCR、跨公司对比或新的前端页面；这些内容统一记录到 `docs/IMPROVEMENT_ROADMAP.md`。

## 2. 报告身份修复

### 2.1 新身份规则

报告 ID 固定为：

```text
{ticker}:{YYYY-MM-DD}:{annual|semi_annual|quarterly}
```

季度报告必须保留真实报告期：

- 一季报：`600900:2025-03-31:quarterly`
- 三季报：`600900:2025-09-30:quarterly`

不得再把 `09-30` 归一化为 `03-31`。

### 2.2 文件名兼容策略

新下载的季度报告文件名包含完整报告期：

```text
长江电力_600900_季报_2025-03-31.pdf
长江电力_600900_季报_2025-09-30.pdf
```

年报和半年报继续使用现有年度文件名，避免无关迁移。解析器同时兼容新旧文件名，但旧格式 `{公司}_{代码}_季报_{年份}.pdf` 无法可靠判断季度，必须返回 `None`，不能猜测为一季报。用户需要重新下载或通过显式 `report_id` 重新摄取这类文件。

### 2.3 RAG 数据迁移

旧索引中的季度数据可能已经发生碰撞，不能自动判断片段属于一季报还是三季报。本次增加 RAG 身份版本标记；检测到旧版本时：

- 年报、半年报数据不受影响；
- 旧季度记录不再被新查询命中；
- 状态接口和日志明确提示需要重新摄取季度报告；
- 新摄取数据使用真实报告期。

不对无法判定归属的旧季度片段做静默迁移。

## 3. 分析任务持久化

### 3.1 存储

`TaskManager` 使用标准库 `sqlite3`，默认数据库为 `data/tasks.sqlite3`。任务至少保存：

```text
task_id, status, progress, result_json, error,
cancelled, retryable, created_at, updated_at
```

不增加第三方依赖。数据库写入使用事务和实例锁；对外 `submit()`、`get()`、`cancel()`、`shutdown()` 接口保持兼容。

### 3.2 重启语义

进程启动时：

- `done`、`failed`、`cancelled` 任务仍可查询；
- 上次进程遗留的 `pending`、`running` 任务转为 `failed`；
- 错误信息固定说明任务因服务重启中断；
- `retryable=true`，但不自动重新调用模型，避免重复成本和重复副作用。

本阶段不持久化 Python callable，因此不提供自动恢复执行。用户可从原分析入口重新提交；后续再基于持久化的分析请求增加专用重试端点。

### 3.3 生命周期

增加终态任务清理能力，按配置保留最近任务，避免数据库无限增长。测试使用临时数据库；生产默认路径已被现有 `data/` 忽略规则覆盖。

## 4. 财务事实和校验

### 4.1 数据模型

新增独立模块定义：

```python
Evidence(page: int | None, quote: str | None, source: str)

FinancialFact(
    metric: str,
    period: str,
    value: float | None,
    unit: str,
    evidence: Evidence | None,
    validation_status: str,
    validation_messages: list[str],
)
```

`AnalysisReport` 新增 `facts` 和 `validation` 字段；原有 `metrics` 保持原结构，前端和旧消费者无需修改即可继续工作。

### 4.2 程序校验

LLM 响应先经过事实转换和校验，再生成兼容的 `metrics`：

- `year` 必须是不晚于报告期年份的合理年份；
- 所有数值必须是有限数；
- `revenue` 不得为负；
- `roe`、`gross_margin` 限制在 `[-1000, 1000]`；
- `debt_ratio` 限制在 `[0, 1000]`；
- 单位由指标定义确定：收入和净利润为 `亿元`，比率为 `%`；
- 重复的 `year + metric` 只保留最后一个有效值，并产生 warning；
- 无效事实不进入兼容 `metrics`，但在 `validation` 中记录原因。

当前 PDF 文本兜底链路无法稳定提供页码，因此 `Evidence` 允许为空；不得伪造页码或引文。页码证据、公式复算和结论级 Evidence 属于后续路线图。

### 4.3 输出兼容

JSON 增加：

```json
{
  "schema_version": 2,
  "facts": [],
  "validation": {"status": "passed|warning|failed", "messages": []}
}
```

已有 `meta`、`dimensions`、`metrics` 字段语义不变。Markdown 暂不增加事实明细，避免改变现有展示。

## 5. 错误处理与安全边界

- SQLite 不可写时，服务启动失败并给出明确路径和原因，不能静默退回内存模式。
- JSON 结果序列化失败时任务进入 `failed`，不写入不完整结果。
- 旧季度文件不做猜测性映射。
- 校验失败不会让整个报告崩溃；报告输出 `warning` 或 `failed` 状态并保留可用指标。
- 本次不修改 MCP 权限、Agent 工具循环和认证策略。

## 6. 测试与验收

所有生产改动遵循测试先行，至少覆盖：

1. `03-31` 和 `09-30` 生成不同的报告 ID；
2. 新季度文件名可准确往返解析，旧季度文件名拒绝猜测；
3. 同公司同年度两份季报可同时存在于 RAG；
4. 任务完成后重新创建 `TaskManager` 仍可查询结果；
5. 重启遗留的 `pending/running` 转为可重试失败；
6. 取消、并发和异常状态保持现有行为；
7. 非有限数、错误年份和越界比率被拒绝；
8. 兼容 `metrics` 只包含通过校验的事实；
9. 现有完整测试套件通过；
10. `git diff --check` 无格式错误。

## 7. 明确不做

- 不自动删除或猜测迁移旧季度向量；
- 不自动恢复中断的模型调用；
- 不引入完整 Agent Planner、Validator Agent 或 Synthesizer；
- 不在本次调整前端模块结构；
- 不提交或推送到远程仓库，最终 Git 整理由用户后续指令决定。
