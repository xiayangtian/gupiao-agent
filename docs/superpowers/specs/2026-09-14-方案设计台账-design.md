# 方案设计台账 — 设计方案

**Date:** 2026-09-14  
**Status:** approved for planning  
**Scope:** 为仓库中已完成设计的方案建立可查询、可执行的台账：用户可查看未完成项目、打开其历史方案，并在当前对话中按既有实施计划直接发起执行。**不包含** Web 页面、额外 CLI、自动扫描 Git 历史推断状态，或对旧设计做未经证据支持的实现结论。

---

## 1. 现状与问题

仓库中的设计文档位于 `docs/superpowers/specs/`，实施计划位于 `docs/superpowers/plans/`，部分实施过程另有 `.superpowers/sdd/` 记录。它们没有统一关联和状态入口。

用户的任务是：在开始新工作前，快速回答“哪些设计已经产出、但还没有实现”。直接浏览目录只能看到文件名，无法区分设计是否已实施，也无法看到实施证据。

## 2. 用户视图模型

台账的首屏必须先显示待处理内容，而不是按目录或日期罗列执行产物。

用户无需点击时应能确认：

1. 哪些方案尚未完成（待实现、实施中、待核实）；
2. 每个未完成项目对应的设计与实施计划，并可直接打开阅读；
3. 对于已有实施计划的未完成项目，如何在当前对话中直接发起执行；
4. 已实现判断所依据的合并提交和验证；
5. 哪些历史方案的状态无法可靠判断。

实施分支、任务报告、Git 提交等属于证明材料，只能附着于方案条目，不能取代方案本身成为主列表。

## 3. 单一事实来源

新增 `docs/superpowers/DESIGN-REGISTRY.md` 作为唯一人工维护的方案设计台账。

文件分为两个区域：

1. **待实现与待核实**：置顶，按状态和最近设计日期排列，满足日常查询；
2. **全部设计**：保存所有已登记方案，便于审计和追溯。

同一方案只在“全部设计”拥有完整主记录；置顶区域只列出待实现与待核实条目的简表及锚点链接，不复制证据字段，从而避免两处状态漂移。

## 4. 条目数据契约

每个已完成设计的方案使用一行 Markdown 表格记录：

| 字段 | 规则 |
|---|---|
| 方案 | 稳定、面向用户的方案名称；与设计文档主题一致 |
| 设计文档 | `docs/superpowers/specs/` 中的相对链接；必须存在 |
| 实施计划 | 对应 `docs/superpowers/plans/` 的相对链接；不存在时写“未创建” |
| 实现状态 | 仅允许 `待实现`、`实施中`、`已实现`、`待核实` |
| 可执行性 | `可直接执行`（实施计划存在且状态为待实现）或 `先补计划`（仅有设计，无实施计划） |
| 实现证据 | 已实现时必须有合并提交短 SHA 与实际验证；其他状态可写“无”或已知分支/进度路径 |
| 更新日期 | 最后一次状态确认日期，格式 `YYYY-MM-DD` |

状态语义：

- **待实现**：设计已完成，未找到已验证并合入 `main` 的实现证据；
- **实施中**：存在对应实施分支或进度记录，尚未完成验证并合入 `main`；
- **已实现**：已合入 `main`，且记录合并提交与验证结果；
- **待核实**：旧文档或历史记录不足，不能可靠断言为待实现或已实现。

禁止通过文件名相似、推测性提交信息或模型判断把条目直接标记为“已实现”。无法确认时必须标为“待核实”。

## 5. 查询、查看与直接执行

台账开头固定为“未完成项目”，列出 `待实现`、`实施中` 与 `待核实` 条目；每条均提供设计文档和实施计划的 Markdown 链接。用户打开台账即可查看尚未完成项目，并从链接阅读方案内容。

对于 `待实现` 且“可执行性”为 `可直接执行` 的条目，用户可在当前对话发出“执行方案：<方案名称>”。助手必须：

1. 从台账解析出唯一条目及其设计文档、实施计划；
2. 先读取二者，确认条目仍为 `待实现` 且实施计划完整；
3. 按既有实施计划在独立分支/工作区执行，而不是重新设计或猜测历史意图；
4. 开始执行前将台账更新为 `实施中`，记录实施分支或进度文件；
5. 只有完成适用验证并合入 `main` 后，才更新为 `已实现`，填写合并提交短 SHA 与验证证据；失败、暂停或范围变化必须保留为未完成状态并说明原因。

`先补计划` 的条目不可直接开始编码。助手应先基于其设计文档补齐实施计划，经用户确认后才可执行。

## 6. 维护流程

1. 新设计文档完成并获用户确认后，创建或更新一条台账记录，初始状态为 `待实现`；有完整实施计划时标记 `可直接执行`，否则标记 `先补计划`；
2. 创建实施分支、进度记录或开始开发后，更新为 `实施中`，证据填写分支名或进度文件；
3. 合并到 `main` 且完成适用验证后，更新为 `已实现`，填写合并提交短 SHA 与验证命令/结果；
4. 放弃方案时保留记录并在证据栏说明原因，状态使用 `待核实`，不得删除历史；
5. 首次建表时仅使用现有设计文档、实施计划、进度报告和 `main` 的合并提交进行回填；证据不足的历史条目一律为 `待核实`。

## 7. 验收标准

- 已登记的每个设计文档都有一个且仅有一个“全部设计”主记录；
- 台账开头可直接看到所有未完成项目及其设计、实施计划链接；
- `待实现` 条目明确标识能否直接执行；
- 对可直接执行条目，用户可通过“执行方案：<方案名称>”使用原实施计划启动工作，而不会重新生成或篡改历史方案；
- 每个 `已实现` 条目都包含合并提交和验证证据；
- 每个 `待核实` 条目明确表示证据不足，不被混同为未实现；
- 新方案设计、实施开始、验证合并三个工作流节点都具有明确的台账更新规则。
